Preamble

Why This Protocol Exists

93% of humanitarian professionals already use AI tools for work. But the presence of AI policy remains at 22% (HLA & DFS, 2025). This gap means sensitive patient data from conflict zones is being processed through commercial LLM APIs without institutional safeguards, risk assessment, or bias auditing.

This protocol does not aim to restrict AI use - that ship has sailed. It aims to make AI safe, auditable, and fair in contexts where data mishandling can endanger lives, and where data itself is structurally biased by the conditions of its collection.

The protocol addresses three interdependent problems:

Confidentiality

Patient data from conflict zones carries extreme risk if exposed

Coordination

Humanitarian data flows through multiple actors, systems, and jurisdictions

Fairness

Conflict-zone data is subject to bias mechanisms absent from standard literature

Scope

Humanitarian medical organizations operating in conflict-affected and resource-limited settings. Builds on: OCHA Data Responsibility Guidelines (2025), IASC Operational Guidance (2021), MSF Data Sharing Policy (2013), ICRC Professional Standards for Protection Work.

Part I: Data Classification

Sensitivity Tiers

Not all data requires the same protections. Sensitivity in humanitarian contexts is determined not only by what the data contains but by the context in which it was collected and what its exposure could enable (Akinci D'Antonoli et al., 2025).

Tier 0 - Public aggregate

Published situation reports, aggregate case counts, program summaries. Already in the public domain.

LLM use: unrestricted.

Tier 1 - Operational non-personal

Supply chain data, logistics, drug stocks, facility capacity. Non-personal but potentially operationally sensitive.

LLM use: APIs permitted after stripping geographic identifiers that could reveal protected facility locations.

Tier 2 - Aggregate health data

Aggregated case counts, attack rates, coverage estimates from DHIS2. No individual records, but small populations can be re-identifiable.

LLM use: zero-retention APIs ONLY. Small denominator test required (n < 15 = suppress).

Tier 3 - Individual patient data

Patient records, clinical narratives, lab results. Anything from which an individual could be re-identified.

LLM use: NEVER transmit to external APIs. Local models only.

Tier 4 - Protection-sensitive

Data whose exposure could lead to violence, persecution, or targeting. Includes: locations of medical facilities in active conflict, ethnicity/tribal affiliation, sexual violence data, data identifying patients treated for conflict-related injuries. NEVER transmit externally under any circumstances. Local processing only. Access-logged and encrypted at rest.

Context-Dependent Sensitivity

The same data can change sensitivity tiers based on context:

DataStable contextConflict context
Malaria case countsTier 1Tier 4 (ethnic targeting along disease-prevalence lines)
Facility locationTier 1Tier 4 (health facilities being attacked)
Rule

When in doubt, classify one tier higher. Reclassify periodically as context evolves.

Part II: LLM Use

Permitted Operations and Safeguards

The primary risk is not "using LLMs" - it is sending identifiable or sensitive data to systems where retention, training, and jurisdiction are outside organizational control.

The first question for any LLM interaction is not which model but what the model is allowed to see.

Three Architectures

Architecture A

LLM builds tools. You run them locally. AI never sees real data.

All tiers ✓

Architecture B

LLM sees de-identified or aggregated data. Zero-retention API.

Tier 0, 1, 2

Architecture C

Local open-weights model. Data never leaves your network.

All tiers ✓ (needs hardware)

Architecture A - Example

Use an LLM to generate a parameterized R script for cohort analysis of TB treatment outcomes. The LLM sees the variable names and analysis logic. Field staff run the script locally on their actual DHIS2 data.

Architecture B - Example

Sending a table of weekly aggregated case counts by district (all cells n ≥ 15) to an API for trend analysis.

Architecture C - Limitation

Smaller models are less capable; validated performance on the specific clinical domain must be demonstrated before deployment.

De-identification Standard (Architecture B)

Before data can be transmitted to any external LLM service:

StepAction
1Remove all 18 HIPAA identifiers (as a minimum baseline)
2Small denominator test: any cell with n < 15 must be suppressed or combined
3Strip geographic precision below the level at which population exceeds 20,000
4Remove temporal precision below the level at which re-identification risk is negligible
5Motivated-intruder test: could someone with local knowledge re-identify individuals?
6Document the de-identification steps in a log retained alongside analysis results

Prohibited Uses

Regardless of architecture: Never use LLMs to make autonomous clinical decisions. Never classify patients by protected characteristics. Never use LLM outputs as evidence in legal proceedings or advocacy without independent verification. Never generate synthetic patient data without expert review.

LLM Vendor Selection Criteria

When commercial LLM APIs are used (Tiers 0-2 only):

CriterionRequirement
Data retentionZero-retention policy (data not stored after processing)
Training exclusionOrganizational data explicitly excluded from model training
Data jurisdictionProcessing occurs in a jurisdiction with adequate data protection laws, AND not party to the conflict
Audit trailAPI logs available to the organization
EncryptionTLS 1.2+ in transit, encryption at rest during processing
Sub-processor transparencyFull list of sub-processors available on request
Incident notificationContractual obligation to notify within 72 hours of a data breach
Part III: Coordination

Coordination and Data Management

Humanitarian health data flows through a complex multi-actor ecosystem: within the organization (field to coordination to HQ), between organizations (cluster coordination, joint assessments), and between the organization and external parties (Ministries of Health, WHO, donors).

Each handoff is a potential point of sensitivity escalation and a potential point of bias introduction.

Data Flow Governance

For every data flow involving AI/LLM processing, document the "5W+H of data flow":

QuestionDocument
WhatData classification tier, variables, volume
WhereSystems, jurisdictions, architectures (from and to)
WhoNamed individual with appropriate authority
WhySpecific analytical question it answers
WhenOne-time, recurring, triggered by what event
HowEncryption, de-identification, access controls

Integration Rules

AI-assisted outputs must be reconcilable with routine DHIS2/surveillance outputs. If an LLM-based trend analysis contradicts the routine epi report, the discrepancy must be investigated before either is acted upon.

AI-generated summaries must cite the underlying data source, variables, and time period. The epidemiologist must be able to reproduce the analysis without the LLM.

AI tools supplement, never replace, the field epidemiologist's judgment. The epidemiologist signs the report, not the model.

Data Quality Management in Degraded Conditions

Before any analytical tool is applied, assess data quality along four dimensions:

Completeness

What fraction of expected records exist? What is missing and why?

Consistency

Do the same events get the same coding? Same case definition across sites?

Timeliness

Lag between event and recording? Between recording and availability?

Representativeness

Who is in the data and who is not?

Minimum viable data quality for LLM-assisted analysis

Completeness > 70% for variables of interest. Consistent case definitions across the analysis period. Lag documented. Known biases in representativeness explicitly stated. If these thresholds are not met, the appropriate output is not an analysis but a data quality assessment - and this is itself a valuable output.

Part IV: Bias & Fairness

Why Standard Algorithmic Fairness Fails in Conflict Settings

Standard algorithmic fairness (Hedden, 2021; Dolata et al., 2022; Kreutzer et al., 2025) assumes:

Data exists for the populations of interest. Protected attributes are known and measurable. The data-generating process is approximately stationary. Missingness is at worst Missing-at-Random (MAR). In humanitarian conflict settings, none of these assumptions hold.

Five Conflict-Specific Bias Mechanisms

1. Survivorship / Access Bias

Only people who reach a health facility enter the dataset. Reaching the facility requires surviving, being mobile, having transport, passing checkpoints, and the facility still being operational.

Mitigation:
  • Always report with an explicit "accessibility caveat"
  • Triangulate with community-based data, remote sensing, or population-movement estimates
  • Apply capture-recapture reasoning where multiple sources exist
  • Never present facility-based attack rates as population-based without adjustment

2. Conflict-Topology Bias

Front lines, checkpoints, besieged areas create a non-random partition of the population into "observable" and "unobservable" subgroups that correlates with conflict exposure.

Mitigation:
  • Map the accessibility structure explicitly
  • Weight by estimated catchment population, not facility reporting volume
  • Flag when results may be driven by accessibility patterns rather than true health differences

3. Temporal Non-Stationarity

A hospital is bombed, a population is displaced, a water system is destroyed. Models trained on pre-event data may be invalid post-event. The model won't tell you it's wrong.

Mitigation:
  • Tag all data with conflict-phase metadata
  • Declare a "model validity horizon"
  • After major conflict events, treat all pre-event models as requiring revalidation

4. MNAR as the Default Condition

In conflict, missingness is informative: data is missing because the facility was attacked, the patient died before admission, the area is too dangerous. Standard imputation methods assume MAR and produce confident wrong answers.

Mitigation:
  • Document the reason for missingness alongside the missing value
  • Use sensitivity analyses under different assumptions
  • Never use LLMs to impute missing health data without expert epi review
  • Report missingness rates prominently alongside all results

5. The Protected Attribute Paradox

The most fairness-relevant attribute may be one that cannot be safely collected - ethnicity in an ethnic conflict, tribal affiliation, displacement status. Recording such attributes in medical records could endanger patients.

Mitigation:
  • Use ecological proxies where safe (geographic catchment as proxy for conflict-side)
  • Apply group fairness metrics at facility/district level, not individual protected attributes
  • Conduct retrospective audits after sufficient anonymization by time lag
  • Never collect conflict-sensitive attributes "for analysis purposes"

The Structural Fairness Layer

Algorithmic fairness operates at the level of model outputs. But structural fairness - fairness in how data systems are designed, who has access, whose questions get asked - is equally important.

Whose questions does the tool answer?

If the tool answers coordination-level questions but not facility-level questions, it structurally privileges HQ decision-making over clinical reality.

Who can access the tool?

If LLM-assisted analysis requires English, internet, and a laptop, it is inaccessible to the majority of national staff who have the most contextual knowledge.

Whose data is legible to the tool?

DHIS2 data from well-equipped facilities is machine-readable. Paper tally sheets from mobile clinics are not. The tool structurally renders invisible the most conflict-affected programs.

Who validates the outputs?

If outputs are validated only by HQ-based analysts who have never visited the context, validation cannot catch errors requiring local knowledge.

Who benefits?

If the tool improves reporting efficiency but not patient care, it extracts data value upward without returning value downward.

Fairness Audit Checklist

Before deploying any analytical tool on humanitarian health data:

Accessibility bias assessment: which populations are and are not represented?
Conflict-topology assessment: does the analysis span different accessibility zones?
Temporal validity: does the data span a major conflict-phase change?
MNAR assessment: is missingness likely informative? Are sensitivity analyses included?
Protected attribute review: are there fairness-relevant attributes that cannot be collected?
Structural fairness review: who designed the question? Who validated? Does value return to the field?
Small-denominator check: could any output enable re-identification?
Model validity horizon declared: what events would invalidate this analysis?

Decision Tree for LLM Use

START: You want to use an LLM for a task involving organizational data. | +-- Does the task involve any patient-level data? | +-- YES -- Can you accomplish it using ONLY de-identified/aggregated data? | | +-- YES -- Apply de-identification standard (Section 2.2) | | | -- Use Architecture B with zero-retention API | | | -- Complete fairness checklist | | +-- NO -- Is local model infrastructure available? | | +-- YES -- Use Architecture C (local model) | | +-- NO -- Use Architecture A (LLM generates tools) | | -- Process real data locally without LLM | +-- NO -- What tier is the data? | +-- Tier 0-1: Commercial API permitted | +-- Tier 2: Zero-retention API only + small-denominator test | +-- Does the task involve ONLY public or reference data? +-- YES -- Unrestricted LLM use. No special documentation required.

Quick-Reference Card

Never send to a commercial LLM

  • Patient names, dates of birth, or any direct identifiers
  • Clinical narratives or consultation notes
  • GPS coordinates of patients or field facilities in active conflict
  • Data on sexual violence, ethnicity in ethnic conflict, or combatant status
  • Any dataset where a subgroup has fewer than 15 individuals

Always document

  • What data was sent, to which service, for what purpose
  • What de-identification steps were taken
  • What fairness biases may affect the analysis
  • What the model validity horizon is

Always ask

  • "Who is NOT in this data?"
  • "What changed in the conflict since this data was collected?"
  • "Would someone with local knowledge be able to identify a person from this output?"
